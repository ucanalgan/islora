# Configuration migration core: Step 3, Phase 1

`island_core::migration::prepare(&str)` is pure: it examines UTF-8 text and returns `Result<MigrationOutcome, MigrationError>`. `Prepared { text }` contains one complete version 2 document; `AlreadyCurrent` means keep the input exactly as supplied; `Future { version }` means preserve the newer document and use read-only compatibility. An error means no migration has been prepared. Error values identify a category and, where applicable, a critical key or line number; they do not include source lines or configuration values.

Schema versions are independent of application versions. Missing `config_version` or `"1"` is legacy; `"2"` is current. Positive versions above 2 are future. Empty, non-decimal, zero, or overflowing versions are invalid. Version 2 documents are not normalized, even if they contain `ui_density`. This core has no byte entry point: callers must reject invalid UTF-8 before constructing `&str`.

| Legacy `ui_density` | Indicator | Media |
| --- | --- | --- |
| `minimal` | `ring` | `compact` |
| `balanced` | `edge` | `standard` |
| `detailed` | `context` | `informative` |

Each valid modern value wins independently. A missing or invalid modern value is derived from a valid legacy value. With no legacy value, absent modern values keep their existing defaults (`edge` and `standard`); an invalid explicit modern value is rejected. An invalid legacy value is rejected when either modern value needs it, but can be removed when both modern values are valid. Successful preparation removes `ui_density` and writes `config_version = "2"` in the same output. The resulting presentation is checked against `Settings::read`.

Duplicate active `config_version`, `ui_density`, `indicator_style`, or `media_layout` assignments are errors, even if identical. Commented lines do not count. Critical values accept the existing simple quoted or unquoted syntax and whitespace-delimited inline comments; malformed quoting, unexpected delimiters, or ambiguous critical lines are rejected. Non-critical assignments, including their values, are not decoded or normalized, and unrelated duplicate keys are retained. Empty and comment-only files are valid legacy input; unsupported bare lines and section headers are rejected rather than guessed. This is a deliberately narrow line-oriented format, not a full TOML parser.

Existing unrelated lines, comments, sensitive values, ordering, UTF-8 BOM, and individual LF/CRLF endings are preserved. A removed legacy line's inline comment becomes a standalone comment. Replaced critical assignments retain their inline comments. New keys are appended in indicator, media, version order, using the predominant line ending (LF on a tie or with no line endings). The source's final-newline status is preserved; when an unterminated final legacy line is removed, the newly exposed final separator is removed if necessary. Input and output are each limited to 1,048,576 bytes; oversized output fails instead of returning a truncated document.

The application presentation reader permits legacy fallback only when the core accepts the legacy input; current and future schemas ignore `ui_density`, and invalid input uses presentation defaults. This is a targeted read-time safeguard. Other settings still use the existing readers. A small BOM compatibility fix lets existing readers and writers recognize a first key following the marker without discarding it. Phase 1 itself only adds the pure core; it does not start migration, modify files, create backups, acquire locks, or change application startup.

Phase 2 (below) owns bounded filesystem reads, locking and Windows file security, protected backup and atomic persistence, post-write verification, startup orchestration, fallback/recovery behavior, and failures. Phase 3 owns any later user-facing migration or recovery workflow.

## Phase 2 status

Startup now migrates. `app.rs` calls `config_store::bootstrap(!second_copy)` once, after the single-instance check and before any window. Bootstrap holds the per-user writer mutex and `config.lock` for one locked transaction:

1. Prepare the storage folder and take an inventory of artifacts through a held directory handle (`ConfigDir`, which refuses reparse points). Stale numeric `.tmp` drafts are deleted; leftover `.new`/`.recover` drafts are never promoted.
2. Read the primary once with a bounded, strictly UTF-8 verified read and classify it (new install, current, future, legacy, invalid).
3. For a legacy primary only, run migration: re-read under the lock, check the failure record's retry rule, call the core `prepare`, and require its output to classify as current.
4. Create a protected backup first: a protected backup named `config.protected.<6-digit sequence>.v<source schema>.<16-hex fingerprint>.bak` holding the exact legacy bytes, created exclusively, read back and set read-only. Then commit the prepared text through a verified draft, a byte check of the source immediately before the rename, a rename by handle, and a post-rename reopen that compares identity and bytes. The rolling `config.toml.bak` is also rewritten with the legacy bytes.
5. After a verified commit, clear any failure record and keep the newest 3 protected backups (a failure of either step is only logged).
6. On a failure before the commit (Backup, Commit, source changed) the primary is left untouched; a Verify failure happens after the rename. In every case startup re-observes the folder and uses its real mode, under the same lock except when the lock was busy or preparation failed, where it observes without the lock and refuses writes. Backup, Commit and Verify failures write a `config.toml.failure` record tied to the source fingerprint; the same source is not retried until it changes. SourceChanged, Unpreparable, I/O errors and Busy leave no record and are tried again at every start.
7. The outcome is stored as a one-shot migration report in the snapshot.

Runtime modes: `Normal`, `LegacyCompatible` (legacy, invalid or unreadable primary kept because migration is disabled, failed or suppressed; settings writes need readable text and ready storage, and the writer still refuses an invalid schema or a duplicate or malformed critical key), `ReadOnly` (future schema; writes refused) and `Recovery` (missing primary with ambiguous artifacts or recovery evidence and no restorable backup; writes refused). A missing primary is restored at startup from a valid rolling `config.toml.bak` if there is one, otherwise from the valid protected backup with the highest sequence, and Reload can repeat that restore while the app runs (see "Recovery and Reload (2D-2)" below).

`--second-copy` starts with migration off (`bootstrap(false)`): it never migrates (startup recovery in the storage preparation still runs under the lock, as for any start). A duplicate launch exits before bootstrap. A plain refresh, which is the lock-free first step of Reload, never migrates, repairs or recovers: a file that becomes legacy, future or repaired while the app runs is reported with its real mode and writes follow that mode (ReadOnly and Recovery refuse, Normal and LegacyCompatible allow). Writes also need ready storage; when startup preparation failed (storage not ready, for example Recovery or a busy lock) they stay refused until Reload repairs the state or the app restarts. Writes compare the locked read with the snapshot and refuse as a conflict if the file changed.

Remaining limits: nothing was tried on the real Windows UI or a real legacy profile; since 2C-4 a failed migration, a Recovery start and a ReadOnly start show a one-time island notice at startup, and Settings > Genel shows a status line while the configuration is not in a normal writable state; transient fallbacks add no island notice, and detailed diagnostics are still lost in release builds; the folder creation and legacy folder rename in `prepare_storage_locked` run by path before the directory handle exists; power-loss durability is unverified (no directory flush after the rename); a write by a non-cooperating process between the final byte check and the rename is not detected; the recovery limits listed in "Recovery and Reload (2D-2)" below (power loss and real crash timing unverified, an unverified restore possible, a fingerprint that is only a change check); and there is no retry cap or backoff for repeated edits of an unmigratable file. See `CONFIG_MIGRATION_ACCEPTANCE.md` for the per-decision status.

Earlier Phase 2 groundwork still applies. Settings reads are bounded to 1 MiB plus one byte and require valid UTF-8, and a failed read does not normalize or truncate the file. The ordinary writer refuses a source that is oversized, has a future or invalid schema version, or has a duplicate or malformed critical key, and refuses output beyond 1 MiB; unsupported lines and section headers do not block a write. The presentation reader applies the `ui_density` fallback only for a classified legacy schema. Fresh files include `config_version = "2"`. The first-start autostart default is skipped without a dialog when the file cannot be written. The DACL is kept across replacement, and so is the owner when it is the current user; a file owned by someone else gets the default owner.

## Recovery and Reload (2D-2)

Startup recovery (`config_recovery::recover_locked`) runs inside the storage preparation, under the writer lock, after the stale-draft sweep, and only when the primary is missing. A present primary is never listed or repaired here, and a present but invalid primary is not repaired. It runs for `--second-copy` as well; only migration is off there.

**Candidates.** The rolling `config.toml.bak` and every protected backup are read without changing them and judged with the primary's rule: current or legacy content is valid, unsupported lines are kept and ignored, a future schema is reported as future, and a critical defect (invalid version, duplicate or malformed critical key), non-UTF-8 bytes or an oversized file is invalid. An empty file, or one with no line the core parser accepts, is never valid. A protected backup whose content does not match the schema and fingerprint in its name is invalid. A read error makes a candidate unreadable.

**Choice.** A valid rolling `.bak` wins. Otherwise the valid protected backup with the highest sequence wins. Rolling and protected files with different contents are not ambiguous. Two different valid protected files at the top sequence are never guessed: nothing is restored. A candidate that is future, invalid or unreadable is skipped and the next one is considered.

**Blocking leftovers.** Any `config.toml.bak.new`, `config.toml.recover`, `config.pre-migration*.bak` or a name that is not valid Unicode blocks every restore (the start is `Recovery`, nothing is written). An unreadable folder listing is treated the same way. `config.toml.new` counts as recovery evidence (no fresh template) but is never restored and does not block. Stale numeric `.tmp` drafts are swept first and do not count as evidence at startup.

**Restore.** `config_commit::restore_primary` writes the chosen candidate's original bytes (including unsupported lines) through a verified draft that carries the backup's owner and DACL, re-reads the backup right before the rename and renames without replacing, so an existing primary is never overwritten; a read-only backup gives a writable primary. It then re-reads the primary and compares identity and bytes, otherwise the result is `CommitUnverified`. No backup is deleted, renamed or changed by a restore. After an I/O error in a restore no other candidate is tried in that run. With no valid candidate, or when blocked, the outcome is as before: no template when there is evidence, and `Recovery`.

**Failure record.** A restore that yields the current schema deletes `config.toml.failure` if present (a delete error is only logged). A restore of an older schema keeps it, so the retry suppression for the same legacy source still applies.

**Older-schema restore.** A legacy backup is restored verbatim; at startup the same lock then migrates it normally (protected backup, commit, verification), unless the kept failure record suppresses the retry. Normal migration afterwards still runs the protected-backup retention (keep 3), so "never deleted" describes the restore, not later retention.

**Reload.** `config_store::reload()` backs the app's "Takvimi ve ayarları yenile" action. It first does the plain lock-free refresh. If storage is ready and the mode is not `Recovery`, that is all (`Refreshed`). If storage is not ready (for example a busy lock at startup) or the mode is `Recovery`, it takes the writer lock with the existing bounded wait (about 100 ms), sweeps stale drafts and runs the same `recover_locked` in the existing folder. It never creates or renames the folder, never writes a template and never migrates. When the primary is present afterwards, a fresh snapshot is observed under the lock and installed by sequence with a fresh `NotNeeded` report, and storage is marked prepared (`Repaired`); a restored older-schema file stays `LegacyCompatible` and is migrated at the next start. A busy lock, a missing folder, a blocked or failed recovery or a primary that is still missing returns `StillRefused` with the lock-free snapshot kept; no config file, template, restore or migration is written (stale numeric drafts are swept first when the lock was taken). The app replaces its kept migration report only after a repair, and no island notice is shown on Reload. This reverses decision D-H for this path: live repair no longer needs a restart.

**Typed save refusals.** A write refused by the runtime mode carries `RefusedMode` (`ReadOnly`, `Recovery` or `NotReady`), taken from the snapshot that refused it. The save message box gives a distinct Turkish text per reason and per restored or not-restored outcome; only its restored `Recovery` and `NotReady` texts point to Reload, the not-restored ones end with "Ayarları kontrol edin.", and the ReadOnly texts do not point to Reload. The calendar address note gives one text per reason (no restored split); only its `NotReady` text points to Reload. Startup autostart stays silent on every refusal. In Settings > Genel the Recovery and restart-needed status lines now also point to Reload.

**What the tests and checks show, and what they do not.** The acceptance tests T (startup restore), R and U (Reload) and the unit tests for the selection, classification and restore primitive pass on temporary folders. Four trial copies (2026-11-27, debug build at `68d10e5`, started with `--second-copy`) restored a lone current-schema `.bak` at startup, restored a legacy `.bak` as `LegacyCompatible`, stayed in `Recovery` with a lone failure record and with a `.bak` next to a `.bak.new`, and left the folder untouched in the last two. Not observed: pressing Reload in a running copy, a restore from a protected backup in the real UI, a migration after a legacy restore, the restart-needed line and the new save-refusal message boxes. Known limits: a `CommitUnverified` restore can leave an unverified primary, which the next start treats normally; the 64-bit fingerprint is a change check, not an integrity check; power loss and real crash timing are unverified, and the by-path folder steps before the handle exists are untested for races.
