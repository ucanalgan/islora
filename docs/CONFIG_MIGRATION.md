# Configuration migration core: Step 3, Phase 1

`island_core::migration::prepare(&str)` is pure: it examines UTF-8 text and returns `Result<MigrationOutcome, MigrationError>`. `Prepared { text }` contains one complete version 2 document; `AlreadyCurrent` means keep the input exactly as supplied; `Future { version }` means preserve the newer document and use read-only compatibility. An error means no migration has been prepared. Error values identify a category and, where applicable, a critical key or line number; they do not include source lines or configuration values.

Schema versions are independent of application versions. Missing `config_version` or `"1"` is legacy; `"2"` is current. Positive versions above 2 are future. Empty, non-decimal, zero, or overflowing versions are invalid. Version 2 documents are not normalized, even if they contain `ui_density`. This core has no byte entry point: callers must reject invalid UTF-8 before constructing `&str`.

| Legacy `ui_density` | Indicator | Media |
| --- | --- | --- |
| `minimal` | `ring` | `compact` |
| `balanced` | `edge` | `standard` |
| `detailed` | `context` | `informative` |

Each valid modern value wins independently. A missing or invalid modern value is derived from a valid legacy value. With no legacy value, absent modern values keep their existing defaults (`edge` and `standard`); an invalid explicit modern value is rejected. An invalid legacy value is rejected when either modern value needs it, but can be removed when both modern values are valid. Successful preparation removes `ui_density` and writes `config_version = "2"` in the same output. The resulting presentation is checked against `Settings::read`.

Duplicate active `config_version`, `ui_density`, `indicator_style`, or `media_layout` assignments are errors, even if identical. Commented lines do not count. Critical values accept the existing simple quoted or unquoted syntax and whitespace-delimited inline comments; malformed quoting, unexpected delimiters, or ambiguous critical lines are rejected. Non-critical assignments, including their values, are not decoded or normalized, and unrelated duplicate keys are retained. Empty and comment-only files are valid legacy input; unsupported bare lines and section headers are rejected rather than guessed. This is a deliberately narrow line-oriented format, not a full TOML parser.

Existing unrelated lines, comments, sensitive values, ordering, UTF-8 BOM, and individual LF/CRLF endings are preserved. A removed legacy line's inline comment becomes a standalone comment. Replaced critical assignments retain their inline comments. New keys are appended in indicator, media, version order, using the predominant line ending (LF on a tie or with no line endings). The source's final-newline status is preserved; when an unterminated final legacy line is removed, the newly exposed final separator is removed if necessary. Input and output are each limited to 1,048,576 bytes; oversized output fails instead of returning a truncated document.

The application presentation reader permits legacy fallback only when the core accepts the legacy input; current and future schemas ignore `ui_density`, and invalid input uses presentation defaults. This is a targeted read-time safeguard. Other settings still use the existing readers. A small BOM compatibility fix lets existing readers and writers recognize a first key following the marker without discarding it. Phase 1 itself only adds the pure core; it does not start migration, modify files, create backups, acquire locks, or change application startup.

Phase 2 (below) owns bounded filesystem reads, locking and Windows file security, protected backup and atomic persistence, post-write verification, startup orchestration, fallback/recovery behavior, and failures. Phase 3 owns any later user-facing migration or recovery workflow.

## Phase 2 status

Startup now migrates. `app.rs` calls `config_store::bootstrap(!second_copy)` once, after the single-instance check and before any window. Bootstrap holds the per-user writer mutex and `config.lock` for one locked transaction:

1. Prepare the storage folder and take an inventory of artifacts through a held directory handle (`ConfigDir`, which refuses reparse points). Stale numeric `.tmp` drafts are deleted; leftover `.new`/`.recover` drafts are never promoted.
2. Read the primary once with a bounded, strictly UTF-8 verified read and classify it (new install, current, future, legacy, invalid).
3. For a legacy primary only, run migration: re-read under the lock, check the failure record's retry rule, call the core `prepare`, and require its output to classify as current.
4. Create a protected backup first: a protected backup named `config.protected.<6-digit sequence>.v<source schema>.<16-hex fingerprint>.bak` holding the exact legacy bytes, created exclusively, read back and set read-only. Then commit the prepared text through a verified draft, a byte check of the source immediately before the rename, a rename by handle, and a post-rename reopen that compares identity and bytes. The rolling `config.toml.bak` is also rewritten with the legacy bytes.
5. After a verified commit, clear any failure record and keep the newest 3 protected backups (a failure of either step is only logged).
6. On a failure before the commit (Backup, Commit, source changed) the primary is left untouched; a Verify failure happens after the rename. In every case startup re-observes the folder and uses its real mode, under the same lock except when the lock was busy or preparation failed, where it observes without the lock and refuses writes. Backup, Commit and Verify failures write a `config.toml.failure` record tied to the source fingerprint; the same source is not retried until it changes. SourceChanged, Unpreparable, I/O errors and Busy leave no record and are tried again at every start.
7. The outcome is stored as a one-shot migration report in the snapshot.

Runtime modes: `Normal`, `LegacyCompatible` (legacy, invalid or unreadable primary kept because migration is disabled, failed or suppressed; settings writes need readable text and ready storage, and the writer still refuses an invalid schema or a duplicate or malformed critical key), `ReadOnly` (future schema; writes refused) and `Recovery` (missing primary with ambiguous artifacts or recovery evidence and no trusted rolling backup; writes refused). A missing primary is restored only from a rolling `config.toml.bak` that passes core validation, and only at startup.

`--second-copy` starts with migration off (`bootstrap(false)`): it observes and never migrates. A duplicate launch exits before bootstrap. Refresh (`reload()`) never migrates, repairs or recovers: a file that becomes legacy, future or repaired while the app runs is reported with its real mode and writes follow that mode (ReadOnly and Recovery refuse, Normal and LegacyCompatible allow); writes stay refused until restart only when startup preparation failed (storage not ready, for example Recovery or a busy lock). Writes compare the locked read with the snapshot and refuse as a conflict if the file changed.

Remaining limits: nothing was tried on the real Windows UI or a real legacy profile; the migration report has no UI consumer, so a failed migration is invisible to the user and diagnostics are lost in release builds; the folder creation and legacy folder rename in `prepare_storage_locked` run by path before the directory handle exists; power-loss durability is unverified (no directory flush after the rename); a write by a non-cooperating process between the final byte check and the rename is not detected; recovery is restart-only and `recover` still rejects a `.bak` with unsupported lines (task 2D-2); protected backups are never used as a restore source; and there is no retry cap or backoff for repeated edits of an unmigratable file. See `CONFIG_MIGRATION_ACCEPTANCE.md` for the per-decision status.

Earlier Phase 2 groundwork still applies. Settings reads are bounded to 1 MiB plus one byte and require valid UTF-8, and a failed read does not normalize or truncate the file. The ordinary writer refuses a source that is oversized, has a future or invalid schema version, or has a duplicate or malformed critical key, and refuses output beyond 1 MiB; unsupported lines and section headers do not block a write. The presentation reader applies the `ui_density` fallback only for a classified legacy schema. Fresh files include `config_version = "2"`. The first-start autostart default is skipped without a dialog when the file cannot be written. The DACL is kept across replacement, and so is the owner when it is the current user; a file owned by someone else gets the default owner.
