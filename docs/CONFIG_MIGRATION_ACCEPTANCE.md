## Security and verification limitations

All migration tests use isolated temporary directories and synthetic data; no real user configuration, real legacy profile or Windows autostart is touched, and the real Windows UI was never run after a migration (the report UI of 2C-4 was only checked on trial copies that could not migrate). Protected backups are made read-only by attribute only, with no ACL lock, and no test asserts the DACL of a protected backup. Folder creation and the legacy folder rename in `prepare_storage_locked` still happen by path before the directory handle exists, with no race or reparse test. Power-loss behavior is unverified: read-back is in-process, there is no directory flush after the rename, and crashes are simulated with hooks and leftover files. A write by a non-cooperating process between the final byte check and the rename is not detected; contention tests use threads in one process. The migration report now has a UI consumer (2C-4): a failed migration, a Recovery start and a ReadOnly start show a one-time island notice at startup, Settings > Genel shows a persistent status while the config is not normal and writable, transient fallbacks add no island notice, and release builds have no console, so detailed fallback diagnostics are still lost. Since 2D-2 a missing primary is restored at startup from a valid rolling `.bak`, else from the valid protected backup with the highest sequence, and Reload can repeat that restore without a restart (D-H reversed for this path); a plain refresh never repairs or migrates and Reload never migrates. A restore re-reads the primary after the rename, and a `CommitUnverified` restore can leave an unverified primary. The 64-bit fingerprint is a change check, not an integrity check. Normal migration still prunes protected backups to 3 after a restore. Restores were observed only at startup on trial copies (2D-2 S10); Reload and a restore from a protected backup were not observed in the real UI. Tests that take the real per-user WriterMutex report Busy while a real Islora is running, so run them with the app closed. The two symlink tests return without testing when the OS lacks symlink privilege. Hardware behavior, external processes and branch protection remain unverified.

The workflow in C runs format, workspace tests, Clippy and release build on Windows for pushes and pull requests to main. Pushes to `v1/foundation` run nothing until a pull request to main exists, and no green run on the current commits is confirmed. A passing CI run cannot satisfy this acceptance gate by itself.
