## Security and verification limitations

All migration tests use isolated temporary directories and synthetic data; no real user configuration, real legacy profile or Windows autostart is touched, and the real Windows UI was never run after a migration. Protected backups are made read-only by attribute only, with no ACL lock, and no test asserts the DACL of a protected backup. Folder creation and the legacy folder rename in `prepare_storage_locked` still happen by path before the directory handle exists, with no race or reparse test. Power-loss behavior is unverified: read-back is in-process, there is no directory flush after the rename, and crashes are simulated with hooks and leftover files. A write by a non-cooperating process between the final byte check and the rename is not detected; contention tests use threads in one process. The migration report has no UI consumer, and release builds have no console, so fallback diagnostics are effectively lost and the user is not told about a failed migration. Repair and recovery are restart-only by design (D-H); refresh never repairs or migrates. `recover` still rejects a rolling `.bak` containing unsupported lines (2D-2). Protected backups are never a restore source. Tests that take the real per-user WriterMutex report Busy while a real Islora is running, so run them with the app closed. The two symlink tests return without testing when the OS lacks symlink privilege. Hardware behavior, external processes and branch protection remain unverified.

The workflow in C runs format, workspace tests, Clippy and release build on Windows for pushes and pull requests to main. Pushes to `v1/foundation` run nothing until a pull request to main exists, and no green run on the current commits is confirmed. A passing CI run cannot satisfy this acceptance gate by itself.
